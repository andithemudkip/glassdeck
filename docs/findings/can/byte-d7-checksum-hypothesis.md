# Byte D7 — universal 6-cycle structure with per-ID XOR offset

On all 9 of the always-on broadcast IDs that originally surfaced D7 movement (`120`, `121`, `129`, `12A`, `12D`, `12E`, `541`, `5A0`, `5B0`), byte D7 is generated by a function with the following confirmed structure:

```
D7  =  cycle[counter mod 6]  ⊕  per_ID_offset  ⊕  f(D0..D6)
```

where:

- **`cycle` is a universal 6-element table** observed identically (up to XOR offset) on every ID.
- **`counter` increments once per broadcast frame** and wraps modulo 6.
- **`per_ID_offset` is a per-ID 8-bit constant** — a small set of values cataloged below.
- **`f(D0..D6)` is a CRC-like compression** of the payload bytes into 8 bits; for static payloads it contributes a constant, so the cycle is observable directly.

The "checksum" framing in the original observation was qualitatively right (D7 is structural, not a data signal) but quantitatively wrong (D7 is not a single CRC over D0..D6). The richer model above explains every observation that motivated the original hypothesis and several that didn't fit it.

## The universal cycle

Reference cycle (`12D`, all-zero payload, observed sorted):

```
0x35, 0x5F, 0x6A, 0x8B, 0xBE, 0xD4
```

Per-ID offset relative to this reference, derived from idle-run-1 (5 s window per ID, dominant-payload-only D7 set):

| ID    | per-ID offset | cycle (sorted) |
|-------|-------------:|----------------|
| `120` |     `0x00`   | `35 5F 6A 8B BE D4` |
| `12D` |     `0x00`   | `35 5F 6A 8B BE D4` |
| `5B0` |     `0x01`   | `34 5E 6B 8A BF D5` |
| `129` |     `0x04`   | `31 5B 6E 8F BA D0` |
| `12A` |     `0x08`   | `3D 57 62 83 B6 DC` |
| `121` |     `0x08`   | `3D 57 62 83 B6 DC` |
| `5A0` |     `0x0E`   | `3B 51 64 85 B0 DA` |
| `541` |     `0x15`   | `20 4A 7F 9E AB C1` |
| `12E` |     `0x1B`   | `2E 44 71 90 A5 CF` |

All 9 D7-checksum-candidate IDs cataloged. The dominant-payload windows that surfaced these cycles vary per ID; offsets are computed against `12D`'s reference (which is itself measured against all-zero payload).

**Two suspicious collisions:** `120`/`12D` both at `0x00` (both with all-zero D0..D6 payloads in their cycle windows) and `121`/`12A` both at `0x08` (with non-identical payloads). With 9 IDs in a 256-element offset space, the Poisson expectation is 0.14 collision pairs; observing two pairs has ≈1% probability if offsets were independent. This briefly motivated a "no per-ID secret" hypothesis (offsets are just `f(payload)`), tested in Parts I–J of the experiment — see "What we tried and refuted" below.

## Structural detail: the cycle is Gray-code-like

The reference cycle's pairwise-XOR closure is exactly `{0x35, 0x5F, 0x6A, 0x8B, 0xBE, 0xD4, 0xE1}` — the 7 nonzero values of the XOR-vector space spanned by `{a=0x35, b=0x6A, c=0xE1}`. The cycle visits 6 of the 8 vertices of the 3-cube:

```
position 0 → {a}    = 0x35
position 1 → {a,b}  = 0x5F
position 2 → {b}    = 0x6A
position 3 → {b,c}  = 0x8B
position 4 → {a,b,c}= 0xBE
position 5 → {a,c}  = 0xD4
```

Each successive position differs from the previous by exactly one of `{a, b, c}` — the definition of a Gray code. The omitted vertices are `{}` = 0x00 and `{c}` = 0xE1.

This is the signature of a small linear feedback generator over a 3-bit state register, not an 8-bit CRC. The cycle is too regular to be CRC-8 output; it is more consistent with a hand-designed 6-state LUT or a 3-bit LFSR with non-trivial output map.

## What's confirmed vs what remains open

**Confirmed structure (all from the d7-byte-character experiment):**

- 6-cycle period across all 8 testable IDs.
- Universal reference cycle up to per-ID XOR offset.
- Gray-code structure in `{0x35, 0x6A, 0xE1}` XOR basis.
- "6 unique D7 values on static-payload IDs" and "100+ on active-payload IDs" both follow from this model (cycle = 6; cycle × payload_compression collisions = many).

**Algorithm not yet reproduced.** Exhaustive search over all 255 polynomials × 256 inits × every reflection setting × every counter-byte placement, on input `(counter, D0..D6=0)`, finds **zero** CRC-8 parameterisations that emit the reference cycle. The algorithm has a hidden input — most likely a per-ID DataID byte (or pair) or a per-ID secret seed pre-shared with the ECU's broadcast scheduler.

## What we tried and refuted

Motivated by the `120`/`12D` and `121`/`12A` offset collisions, we hypothesised that the "per-ID offset" might actually be `f(D0..D6)` with no per-ID secret at all. Three searches against this:

- **CRC-8 over D0..D6, every variant + per-ID seed.** No 9/9 fit. Best aggregate: 3/9 on CRC-8/DARC.
- **CRC-8 with reversed byte order.** No 9/9 fit either.
- **Direct table-constraint solve from four single-non-zero-byte payloads** (`5B0`, `129`, `5A0`, `12E` each have exactly one nonzero byte in D0..D6 in their cycle windows). These give exact constraints on `T^n[byte] = target` for any CRC-8 table T. No polynomial across all 255 satisfies even 3 of 4 constraints, in either byte order, either reflection.

**Conclusion: f is not a standard CRC-8 over D0..D6 alone.** Either (a) the algorithm includes a per-ID DataID input we don't see on the bus and the two offset collisions are honest birthday-paradox noise (~1% prior, low but possible), or (b) the byte-compression isn't a CRC-8 at all (Pearson hash, custom permutation table, etc.). Current data cannot distinguish.

## Why this matters

Three downstream implications.

**For TX in Phase 5: replay yes, novel no.**

- *Replay-style TX is viable.* The dashboard can broadcast a frame with a payload it has already observed on the bus by pinning D7 to one of the 6 observed cycle values at the matching counter position. Steady-state cycle lock-in takes ≤60 ms (six 10 ms frames on any of the busy IDs).
- *Novel-payload TX is blocked.* For any payload the ECU has not emitted itself, the dashboard cannot synthesise a valid D7. Mode toggle, trip reset, and other dashboard-originated active features will probably need either to wait until we reproduce the algorithm, or to observe the OEM dash's TX cycle directly on the bus (so we can replay those exact bytes when the dashboard wants to send the equivalent message).

**For decode-target priorities, D7 is already explained.** Time spent hunting for "which signal lives at D7" is wasted on 9 of the 11 always-on IDs — the byte is fully structural. The exceptions remain `540` D7 and `450` D7, both of which read static `0x00` in every window tested; those two are not yet known to follow the same cycle structure, and need a capture with more `540`/`450` payload movement to characterise.

**For confidence in our overall decoding model**, this is a clean confirmation that the ECU's broadcast scheduler uses sequence-counter-style E2E protection — which is itself useful prior knowledge: any signal we decode on D0..D6 has 6 broadcast frames per cycle, and we should expect a sliding window of `<= 6 × period_ms` worth of D7 history to lock the cycle phase before TX.

## Open

- **Distinguish "per-ID secret" from "non-CRC payload hash"** — needs a constant-payload window for an ID we haven't characterised yet (probably surfaced by future captures), OR a capture where the *same payload* is observed on two different IDs (would directly compare offsets). If two IDs ever broadcast the same D0..D6 and we see different D7 cycles, that proves the per-ID secret exists.
- **`121` shared `0x08` test.** Compute `121`'s offset on its *non-dominant* payloads (the 9 distinct payloads observed in the idle window). If `121`'s offset stays at `0x08` for every payload, the offset is per-ID. If it shifts with payload, the offset is `f(payload)`. Cheap desk follow-up.
- **`540` D7 and `450` D7.** Both static `0x00` in every window tested. Either they follow a different rule, or the captures we have don't move their payloads enough to surface the cycle. A capture with engine-on stationary inputs varying ABS state / brake pressure / mode should move `540` enough; `450` may need motion.
- **Counter-phase alignment.** Each of the 9 cycles in the table starts at a different position because the captures begin at arbitrary times. A single-capture cross-ID analysis (`(timestamp mod 60 ms, ID, D7_position)` for all IDs together) would tell us whether the per-ID counters share a global phase or run independently.
- **If we genuinely want the algorithm**, the remaining angles are external — look up other open-source KTM/Husqvarna projects for documented per-message DataIDs or LFSR seeds, or read the ECU's binary if obtainable. CAN-data-only search has run out of constraints.
