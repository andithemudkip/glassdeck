# Byte D7 — fully reproduced: 6-cycle XOR universal-linear hash of payload

On all 9 of the always-on broadcast IDs that originally surfaced D7 movement (`120`, `121`, `129`, `12A`, `12D`, `12E`, `541`, `5A0`, `5B0`), byte D7 is generated by:

```
D7  =  cycle[counter mod 6]  ⊕  f(D0..D6)
```

where:

- **`cycle` is a universal 6-element table** observed identically on every ID — the same six bytes show up on every ID once the per-frame payload contribution is XORed out.
- **`counter` increments once per broadcast frame** and wraps modulo 6.
- **`f(D0..D6)` is a 5-bit GF(2)-linear hash of the payload bytes.** Each output bit is the XOR of a specific subset of the 56 input bits, with no affine constant (`f(zeros) = 0`). Reproduced exactly: 1040 (payload, `f(payload)`) constraints, 1040 verify against the closed-form. See "`f(D0..D6)` — closed form" below.

There is **no per-ID secret, seed, or DataID** in this model. The "per-ID offset" originally cataloged was a measurement artifact: each ID was characterized using the *dominant payload* of its capture window, so we observed `f(dominant_payload_for_ID)`, mistook the resulting constant for a per-ID property, and read identical numbers ("two collisions") when two IDs happened to share their dominant payload (e.g. both `120` and `12D` had all-zero payloads ⇒ both saw `f(zeros) = 0`).

## The universal cycle

Reference cycle (`12D`, all-zero payload, time-ordered):

```
0x35, 0x5F, 0x6A, 0x8B, 0xBE, 0xD4
```

`f(payload)` at the dominant payload of each ID's idle-run-1 measurement window — these are samples of `f`, **not** per-ID constants:

| ID    | dominant payload (`D0..D6`) | `f(payload)` |
|-------|-----------------------------|-------------:|
| `120` | `00 00 00 00 00 00 00`      | `0x00` |
| `12D` | `00 00 00 00 00 00 00`      | `0x00` |
| `5B0` | (sole observed)             | `0x01` |
| `129` | (idle-run dominant)         | `0x04` |
| `12A` | (idle-run dominant)         | `0x08` |
| `121` | `00 00 00 00 04 88 00`      | `0x08` |
| `5A0` | (sole observed)             | `0x0E` |
| `541` | (idle-run dominant)         | `0x15` |
| `12E` | (idle-run dominant)         | `0x1B` |

The full per-payload extraction (`scripts/d7_offset_per_payload.py`) surfaces ~1500 distinct payloads across the corpus, each with a single deterministic `f(payload)` value. `541` alone contributes ~980 payloads spanning all 32 values of the 5-bit output range.

## Structural detail: the cycle is Gray-code-like

The reference cycle's pairwise-XOR closure is exactly `{0x35, 0x5F, 0x6A, 0x8B, 0xBE, 0xD4, 0xE1}` — the 7 nonzero values of the XOR-vector space spanned by `{a=0x35, b=0x6A, c=0xE1}`. The cycle visits 6 of the 8 vertices of the 3-cube:

```
position 0 → {a}    = 0x35
position 1 → {a,b}  = 0x5F
position 2 → {b}    = 0x6A
position 3 → {b,c}  = 0x8B
position 4 → {a,b,c}= 0xBE
position 5 → {a,c}  = 0xD4
```

Each successive position differs from the previous by exactly one of `{a, b, c}` — the definition of a Gray code. The omitted vertices are `{}` = 0x00 and `{c}` = 0xE1.

This is the signature of a small linear feedback generator over a 3-bit state register, not an 8-bit CRC. The cycle is too regular to be CRC-8 output; it is more consistent with a hand-designed 6-state LUT or a 3-bit LFSR with non-trivial output map.

## `f(D0..D6)` — closed form

`f: bytes[7] → uint5`, fully reproduced by `scripts/d7_payload_hash_search.py`. Each of the 5 output bits is the XOR of a specific subset of the 56 payload bits. Indexed as `Di.j` = bit `j` (LSB=0) of payload byte `Di`:

```
f_bit_0  =  D0.0 ⊕ D0.4 ⊕ D1.2 ⊕ D1.3 ⊕ D1.7 ⊕ D2.0 ⊕ D2.3 ⊕ D2.5
          ⊕ D4.0 ⊕ D4.1 ⊕ D4.4 ⊕ D4.6 ⊕ D5.4 ⊕ D6.1 ⊕ D6.2 ⊕ D6.5 ⊕ D6.7

f_bit_1  =  D0.0 ⊕ D0.3 ⊕ D1.3 ⊕ D1.5 ⊕ D1.7 ⊕ D2.0 ⊕ D2.1 ⊕ D2.4 ⊕ D2.6
          ⊕ D3.3 ⊕ D4.1 ⊕ D4.2 ⊕ D4.5 ⊕ D4.7 ⊕ D5.0 ⊕ D5.7 ⊕ D6.0 ⊕ D6.2 ⊕ D6.3 ⊕ D6.6

f_bit_2  =  D0.0 ⊕ D0.1 ⊕ D0.2 ⊕ D0.5 ⊕ D1.2 ⊕ D1.3 ⊕ D1.5 ⊕ D1.7
          ⊕ D2.0 ⊕ D2.1 ⊕ D2.2 ⊕ D2.3 ⊕ D2.7 ⊕ D3.0 ⊕ D3.5
          ⊕ D4.1 ⊕ D4.2 ⊕ D4.3 ⊕ D4.4 ⊕ D5.1 ⊕ D5.4 ⊕ D5.7
          ⊕ D6.0 ⊕ D6.2 ⊕ D6.3 ⊕ D6.4 ⊕ D6.5

f_bit_3  =  D0.1 ⊕ D0.3 ⊕ D0.5 ⊕ D1.0 ⊕ D1.3 ⊕ D2.1 ⊕ D2.2 ⊕ D2.3 ⊕ D2.4
          ⊕ D3.1 ⊕ D3.3 ⊕ D4.0 ⊕ D4.2 ⊕ D4.3 ⊕ D4.4 ⊕ D4.5 ⊕ D5.2
          ⊕ D6.1 ⊕ D6.3 ⊕ D6.4 ⊕ D6.5 ⊕ D6.6

f_bit_4  =  D0.0 ⊕ D0.1 ⊕ D0.3 ⊕ D0.5 ⊕ D1.1 ⊕ D1.2 ⊕ D1.3
          ⊕ D2.2 ⊕ D2.4 ⊕ D3.2 ⊕ D4.0 ⊕ D4.3 ⊕ D4.5
          ⊕ D5.3 ⊕ D5.4 ⊕ D5.7 ⊕ D6.0 ⊕ D6.1 ⊕ D6.4 ⊕ D6.6
```

Properties:

- **Linear, not affine.** No bit has a constant term; `f(zeros) = 0` falls out automatically.
- **Output entropy distribution.** Each output bit's mask has popcount in `{17, 20, 22, 20, 27}` — roughly half the 56 input bits — exactly the entropy profile of an 8-bit CRC truncated to its low 5 bits. The algorithm is almost certainly a CRC-8 (or an LFSR-style 5-bit equivalent) with the high 3 bits discarded.
- **Verification.** 1040 unique (payload, `f(payload)`) constraints, fitted with zero free parameters left over after the 57-unknown Gaussian elimination. 1040/1040 verify against the closed form. No cross-ID conflicts.
- **Subsumes every standard CRC-8 variant.** GF(2)-affine search covers every CRC-8 (poly × init × refin × refout × xorout), so the earlier failed CRC-8 sweep over 4 single-byte constraints simply ran out of constraints — with 1040 constraints the linear fit succeeds. Whether the resulting linear map corresponds to a *standard* CRC-8 (e.g., AUTOSAR's 0x2F, J1850's 0x1D) or a custom Husqvarna polynomial is open, but irrelevant for use: the masks above ARE the algorithm.

## What's confirmed

- 6-cycle period across all 8 testable IDs.
- Universal reference cycle (no per-ID variation once `f(payload)` is XORed out).
- Gray-code structure in `{0x35, 0x6A, 0xE1}` XOR basis.
- `f` is a stateless 5-bit GF(2)-linear function of `D0..D6` — **closed form recovered**, verified 1040/1040.
- "6 unique D7 values on static-payload IDs" and "100+ on active-payload IDs" both follow from this model (cycle = 6; cycle × `f(payload)` collisions = many).

**Remaining unknowns** (none required for TX synthesis given a phase-lock window):

- The Gray-code cycle's *generator* (LUT vs. tiny LFSR) is not formally identified — but the cycle table itself is, so this is a curiosity, not a blocker.
- The counter's phase: where each ID's counter is at any given absolute time. Resolvable by listening for ≤6 frames before transmitting.

## What we tried and refuted

- **"Per-ID secret" hypothesis.** Refuted by `scripts/d7_offset_per_payload.py` (2026-06-23). Every ID with multiple payloads in the corpus shows the cycle XOR offset varying with payload, single-valued per payload. `121`'s shared-`0x08` collision with `12A` was specific to the `00 00 00 00 04 88 00` payload; on `121`'s 26 other payloads, `f` takes 14 other values. The original two collisions (`120`/`12D` at `0x00`, `121`/`12A` at `0x08`) are accounted for by the IDs sharing a dominant payload in the original measurement window.
- **`g(canID) → offset` as a function of CAN ID** — refuted by `2026-06-23-d7-offset-id-search`. No GF(2)-linear, affine, CRC-8, or `(a·ID + b) mod K` fit. Now moot: there is no per-ID component to model.
- **CRC-8 as `f(D0..D6)`, original 4-constraint sweep** — failed on too-few constraints. Superseded by the 1040-constraint GF(2)-affine fit, which succeeds and (since GF(2)-affine subsumes every CRC-8 variant) implicitly identifies the polynomial too. The original sweep's failure was a sampling artifact, not a real ruling against CRC-shaped algorithms.

## Why this matters

Three downstream implications.

**For TX in Phase 5: replay and novel-payload TX both unblocked**, modulo a one-time phase-lock window per ID.

- *Replay-style TX is viable.* The dashboard can broadcast a frame with a payload it has already observed on the bus by pinning D7 to one of the 6 observed cycle values at the matching counter position. Steady-state cycle lock-in takes ≤60 ms (six 10 ms frames on any of the busy IDs).
- *Novel-payload TX is unblocked.* For any novel `D0..D6`, compute `f(D0..D6)` from the closed form above, then XOR with `cycle[counter mod 6]` where `counter` is read off the most recent listen-only frames on that ID. The only remaining ECU-private state is the counter phase, and it is observable from one cycle (≤6 frames) of listening.

**For decode-target priorities, D7 is already explained.** Time spent hunting for "which signal lives at D7" is wasted on 9 of the 11 always-on IDs — the byte is fully structural. The exceptions remain `540` D7 and `450` D7, both of which read static `0x00` in every window tested; those two are not yet known to follow the same cycle structure, and need a capture with more `540`/`450` payload movement to characterise.

**For confidence in our overall decoding model**, the model is now simpler than before: one universal cycle, one universal mixer `f`. The ECU's broadcast scheduler uses sequence-counter-style E2E protection — any signal we decode on D0..D6 has 6 broadcast frames per cycle, and we should expect a sliding window of ≤ 6 × period_ms worth of D7 history to lock the cycle phase before TX.

## IDs outside the cycle family: `540` and `450`

The cycle model implies D7's high 3 bits == cycle's high 3 bits, which are never `000` (every value in `{0x35, 0x5F, 0x6A, 0x8B, 0xBE, 0xD4}` has at least one of the top 3 bits set). So `D7 = 0x00` is impossible under the cycle model regardless of payload.

Applied to `540` and `450` (see `scripts/d7_540_450_check.py`):

| ID    | frames | distinct payloads | D7 values | cycle-model consistent |
|-------|-------:|-----------------:|-----------|:---------------------:|
| `540` | 13,455 |             1,027 | `{0x00}` (100%) | 0 / 1,027 pairs |
| `450` | 27,518 |                 1 | `{0x00}` (100%) | 0 / 1 pairs |

`540`'s 1,027 distinct payloads varying D0..D6 with D7 frozen at `0x00` rules out the cycle scheme decisively — there's plenty of payload movement, and the predicted `f(payload)` lands at non-cycle values (e.g. `0x16`, `0x19`, `0x0F`, `0x07`, `0x08` for the first few payloads tried). `450` doesn't vary its payload in the corpus, but its D7 is also flat zero across 27k frames.

**Reconfirmed across the larger 14-session corpus** by [[2026-06-30-unknown-byte-corpus-sweep]]: `540` D7 = 18,809 frames / 0 non-zero; `450` D7 = 38,507 frames / 0 non-zero. The "always-zero" claim holds across every condition exercised so far — cold boot, idle (cold/warm/hot), full RPM sweep, post-kill decay, gear cycling, clutch toggling, kill toggling, side-stand toggling, throttle sweep engine-off, wheel-spin engine-off, wheel-spin engine-on, shift-lever-vs-clutch, front-wheel hand-spin, front-wheel decay + high-beam toggle.

**Practical implication:** D7 on `540` and `450` is unprotected — either reserved (always-zero placeholder) or a different scheme that is currently inactive. For replay or novel TX on these IDs, the dashboard simply emits `D7 = 0x00`. No phase-lock, no `f` computation required.

The "cycle family" is therefore the 9 catalog IDs (`120`, `121`, `129`, `12A`, `12D`, `12E`, `541`, `5A0`, `5B0`); `540` and `450` are outside the family.

## Open

- **Identify the underlying CRC-8 / LFSR polynomial.** The 5-bit linear map is fixed; reconstructing the underlying 8-bit CRC poly (if any) is a small additional puzzle that would give the additional 3 high bits "for free" and possibly identify a standard variant for documentation. Nice-to-have, not needed for TX.
- **Counter-phase alignment across IDs.** Now decoupled from the `f` puzzle. Useful for minimizing the listen-before-TX window if a global counter exists (one phase-lock unlocks all IDs); otherwise per-ID phase-lock is still cheap.
- **`450` payload movement.** All 27k captured frames carry the same payload, so we can't say *anything* about `450` beyond "D7=0 here". A capture that moves `450`'s payload (likely engine-on with motion-related input variation) would let us test whether `450` follows `540`'s "D7 always zero" scheme or has its own movement we haven't seen yet.
